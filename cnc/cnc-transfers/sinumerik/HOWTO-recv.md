# `./recv` — забрати програму зі стійки у файл

Обгортка над `./sniff` цього каталогу. `sniff` слухає лінію й повертає сирі
байти, `recv` знає, що це за керування, і робить із них читабельний `.nc`.

## Найкоротше

```
cd ~/cnc-transfers/sinumerik
./recv
```

**Спершу команда, потім `START` на стійці.** Це не побажання: `sniff` після
відкриття порту робить `tcflush`, щоб не наловити чужого з буфера. Якщо стійка
вже передає, разом зі сміттям викидається початок програми — так ми одного разу
втратили заголовок і три перші кадри.

Обовʼязкових аргументів нема. Файл ляже в поточний каталог з імʼям на кшталт
`20260806_121500_399B.nc`. Своє імʼя — першим аргументом:

```
./recv test/mpf1.nc
```

Наявний файл не затирається — інструмент відмовляється.

## `DC1` шлеться сам

`SD 5012 = 00000001` — код пристрою на вивід стоїть як Xon/Xoff
character-controlled, тож стійка **чекає символ Xon**, перш ніж почати віддавати.
`START` на пульті лише зводить курок.

Тому `recv` шле `DC1` (0x11) кожні 2 с, поки дані не пішли, і замовкає щойно вони
пішли. Окремо просити про це не треба. Вимкнути — `--no-dc1`; без нього
вивантаження просто стоятиме.

## Порядок дій на стійці

1. `DATEN EIN-AUS` → `DATEN-AUSGABE`
2. `Ausgabeschnittstelle` ← `1`, тип даних — керуючі програми, номер програми
3. запустити `./recv` на лаптопі
4. `START` (софткнопка 4)

Дані можуть піти не одразу — у нас було 56 с від `START` до першого байта.
Це не зависання.

**`CTS=0` під час видачі — норма, не обрив.** Мануал: у 810/820 сигнал RTS
стійки лишається в нулі, поки вона віддає.

## Що вона робить із даними

| Крок | Що саме |
|---|---|
| знімає біт парності | лінія 7E1, восьмий біт — парність. Без цього пробіл (0x20) ляже у файл як 0xA0 |
| ріже лідер і хвіст | стійка обрамляє програму нулями (у нас було 139 + 118 байт) |
| зводить кінці рядків | стійка віддає `LF CR CR`, у файл пишеться `CRLF` |

Що **не** робить: не чіпає кінцевих пробілів у кадрах — їх стійка ставить сама,
на передачу назад вони не впливають, `./send` їх однаково зрізає.

Приклад виводу:

```
received: 675 B in 72.7 s
longest gap inside the data: 0.45 s at byte 260 (--idle is 1.50 s)
stripped NUL: leader 139 B, trailer 118 B
line endings normalised to CRLF, 19 blocks
saved: /home/…/test/mpf1.nc  (399 B)
```

## `longest gap` — на що дивитись

`--idle` типово `1.5` с: стільки тиші означає «передача скінчилась». Стійка
передає нерівно — 675 байт у нас ішли 16.6 с при 0.7 с чистого дроту. Якщо
`longest gap` підповзе до `--idle`, файл почне обриватись **посеред програми**,
і зовні це виглядатиме як нормально завершений прийом.

Тому інструмент друкує найдовшу паузу з номером байта й попереджає
`<-- close to --idle, RAISE IT`, коли вона переходить половину. Побачив таке —
піднімай: `./recv --idle 5`.

## Попередження, які вона друкує

| Текст | Що означає |
|---|---|
| `WARNING: N bytes do not have even parity` | лінія не 7E1: не та швидкість або не той формат. Файл усе одно записується |
| `WARNING: N NUL bytes inside the program body` | нуль **усередині** тіла, не в лідері: збій на лінії або не той формат. Прибрано, але файл треба перевірити перед відправкою назад |

## Решта прапорців

| Прапорець | Типово | Для чого |
|---|---|---|
| `--wait` | `600` | скільки чекати першого байта |
| `--idle` | `1.5` | скільки тиші означає кінець |
| `--port` | авто | коли портів кілька; прокидається в `sniff` як є |
| `--no-dc1` | — | не слати `DC1` (типово шлеться) |
| `-b` | `9600` | швидкість |
